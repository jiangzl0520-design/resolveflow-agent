# Day 00：Agent 项目基础认知

## 完成内容

明确 ResolveFlow 要解决企业售后工单调查与退款处置，而不是做普通聊天机器人；同时确定项目必须具备完整后端、真正 Agent 循环、上下文工程、可观测评估和人机协同。

## 完整流程

```text
用户提出售后目标
→ Agent识别当前目标和缺失事实
→ 选择订单、物流、签收证明、政策等工具
→ 将工具返回记录为Observation
→ 根据新事实修改计划
→ 后端Policy检查硬规则
→ 高风险操作暂停并等待人工审批
→ 执行后再次查询并验证结果
```

## 必须区分的概念

- History：完整对话过程，包括用户改口和旧订单号。
- Agent State：当前任务执行到了哪里、当前订单号、计划、证据和终止原因。
- Context：本轮真正交给模型的必要信息，不等于全部History。
- Memory：跨任务保留的稳定用户偏好，例如偏好中文回复。
- RAG Evidence：从企业知识库召回的外部证据，不能覆盖系统规则。

模型负责目标理解、工具选择、证据冲突判断和计划修订；后端负责权限、金额、退款资格、审批绑定和幂等执行。订单号从10086改成10087时，History保留修改事实，State切换到10087，旧证据、方案和审批失效并重新调查。

## 失败与安全

模型可能漏看参数变化、误解审批或受到Prompt Injection，因此高风险写操作不能只靠Prompt约束。信息不足、证据冲突、权限不足或审批缺失时，正确行为是暂停、补查或转人工，而不是强行退款。

## 测试证据

Day00属于项目认知与架构定界，没有新增运行代码；验收证据是围绕订单改号、签收证据冲突、退款审批和History/State/Context/Memory分类完成的场景推演，以及形成的项目蓝图和30天路线。

## 与后续Day的关系

Day00确定了项目边界；Day01—Day07搭建可复用后端和工具基础，Day08—Day10形成Agent闭环与人工审批，Day12以后完善知识与上下文工程。

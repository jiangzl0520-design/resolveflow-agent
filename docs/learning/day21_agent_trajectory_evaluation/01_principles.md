# Day21：Agent 任务、轨迹与工具评估原理

## 1. 今天解决的真实问题

只检查 Agent 的最终答案会产生严重误判。例如 Agent 先尝试对错误订单退款，失败后才查询正确订单，最后碰巧输出“转人工审核”。最终答案虽然正确，但过程已经暴露出越权、串单和资金风险，不能算合格。

Day21 把 Day20 的统一离线评估框架升级为“结果与过程同时验收”：同一条 Golden Case 同时约束最终状态、工具选择、工具参数、步骤预算、业务 Policy 和失败归因。六个维度必须全部通过，案例才通过。

## 2. 从输入到评分报告的完整流程

1. Harness 加载并校验版本化数据集和运行配置，先拒绝结构错误或包含敏感数据的样本。
2. Baseline 与 Candidate 在完全相同的 Case、配置和随机种子下执行。
3. 正常、边界和对抗案例进入真实 `AgentRunner`：Planner 读取当前 State，选择下一步，Runner 做安全校验，ToolExecutor 执行真实 ToolDefinition，Observation 回写 State，完成校验器决定是否允许结束。
4. 每个 Step 被转换为稳定、可比较的评估轨迹：Action、Tool 名称/版本、参数、是否真正执行、状态、错误类型和完成校验码。随机 UUID、耗时和时间戳不进入离线评分结果，避免相同版本重复运行时产生无意义差异。
5. 六类组件失败样本使用明确标注的 typed failure fixture，专门验证 `planner/retriever/tool/context/policy/model` 归因规则，不伪装成真实组件调用。
6. `TrajectoryRuleEvaluator` 对每个 Case 做六维确定性评分。
7. Harness 汇总 Baseline/Candidate、分类准确率、改进项、回归项和质量门禁。
8. Day21 报告再增加每个维度的通过率、归因分布，以及“最终结果正确但轨迹不安全”的 Case 清单。

## 3. 六个评分维度及其关系

### 3.1 Task outcome：最终任务结果

检查 `final_status`、`termination_reason`、`final_outcome` 和 `error_code` 是否符合标注。这只能证明“最后停在哪里”，不能证明中间过程安全，所以它是必要条件，不是充分条件。

### 3.2 Tool selection：工具选择

评分器同时检查：

- 必须调用且成功的工具是否齐全；
- Agent 尝试过的工具是否都在当前 Case 的允许集合中。

这里使用“尝试过”而不是只看“成功执行过”。因为后端成功拦截 `refund_execute` 只能证明防线有效，不能证明 Agent 的决策正确；Agent 仍应因选择危险工具而扣分。

### 3.3 Tool arguments：工具参数

正确工具加错误参数依然是错误行为。订单和物流证据都绑定权威 `order_id`；订单号由 10086 改为 10087 后，旧订单 Observation 和审批不能继续使用。Policy 查询还要绑定正确的工单类别与地区。

参数评分与后端资源绑定校验互补：后端 Policy 负责运行时阻止越权，离线 Evaluator 负责发现 Agent 曾经产生过这种错误决策并阻止版本发布。

### 3.4 Step efficiency：步骤效率

步骤少并不天然更好，必须先满足证据完整和安全。在此基础上检查：

- 总 Step 不超过 Case 的预算；
- 每个工具的尝试次数不超过预算；
- 临时依赖故障允许有限重试，永久错误和无关工具不能靠无限尝试掩盖。

因此“效率”衡量的是完成正确流程所需的额外浪费，而不是鼓励跳过证据。

### 3.5 Policy compliance：策略合规

检查轨迹中是否出现未审批退款、错误资源绑定、当前步骤不允许的工具、缺少证据就提前结束等行为。即使危险动作被后端拦截，Agent 轨迹仍判失败。

这体现模型与后端的职责分工：模型提出候选下一步，确定性的 Security Policy、Completion Verifier 和退款 Policy 决定动作能否执行；评估体系再检查模型是否经常撞这些硬门禁。

### 3.6 Failure attribution：失败归因

仅记录“任务失败”不足以优化系统。归因至少区分：

- `planner`：决策结构或规划逻辑失败；
- `retriever`：知识召回或检索依赖失败；
- `tool`：工具选择、调用或依赖失败；
- `context`：必需上下文装配或安全检查失败；
- `policy`：确定性业务规则拒绝；
- `model`：模型网关、Provider、超时或结构化输出失败。

归因与可观测性的关系是：Trace 提供“在哪个组件、哪个 Span、哪个错误码失败”的事实，Evaluator 检查系统是否把失败归到正确优化责任域。错误归因会让团队改错模块。

## 4. 为什么六维采用 AND，而不是平均分

本项目的硬安全维度不能被其他高分抵消。一次未审批退款尝试不能因为最终答案、语言质量和步骤效率很好就被平均成及格。因此单 Case 的规则是：

`最终结果通过 AND 工具通过 AND 参数通过 AND 效率通过 AND Policy 通过 AND 归因通过`

汇总准确率用于版本比较；单 Case 的硬门禁用于防止危险路径混入候选版本。以后可以为低风险语言质量增加软分，但不能替代硬门禁。

## 5. Baseline 为什么有价值

Day21 的 Baseline 故意只追求最终答案。它会先插入一次提前结束、未知工具、错误订单、无审批退款或无关查询，然后再走安全流程，因此最后结果仍可能正确。

固定 18 个合成案例中：

- Baseline 的最终结果维度是 18/18；
- Baseline 的整体轨迹仅 2/18；
- 16 个案例被识别为“最终结果碰巧正确，但轨迹不合格”；
- Candidate 六个维度和整体均为 18/18。

这组对照直接证明：轨迹评估捕获了最终答案评估看不见的真实风险。

## 6. 确定性规则与 LLM Judge 的边界

Day21 使用确定性规则评价可以精确判断的事实：工具名、参数、次数、状态、错误域、审批与资源绑定。这些项目不应交给 LLM 猜测，因为代码规则更稳定、便宜、可复现且可审计。

LLM Judge 更适合评估“解释是否清楚、理由是否充分、语义是否忠实”等难以完全枚举的软质量，它属于 Day22。正确组合是先过 Day21 硬门禁，再用 Judge 评价软质量，而不是用一个 Judge 总分覆盖安全规则。

## 7. 与前后 Day 的关系

- Day18 的 Trace 提供跨组件事实和 failure domain；Day21 把这些事实变成可回归的判分维度。
- Day19 的 Metrics/Logs 发现线上趋势和单次事故；Day21 在离线发布前阻止已知坏轨迹回归。
- Day20 提供数据加载、隔离执行、版本指纹、Baseline/Candidate 和质量门禁；Day21通过可插拔 Evaluator 扩展评分语义。
- Day22 将在硬规则之外加入 LLM Judge 与人工校准，处理解释质量等语义问题。

## 8. 当前证据与明确边界

本次 18 条数据是固定、去标识化的合成门禁集，不代表线上真实准确率。12 条正常/边界/对抗案例运行真实 `AgentRunner`；6 条组件归因案例是明确标注的 typed fixtures，只验证归因评分接口，不能宣称已经对六个生产依赖都做了故障注入。确定性 Planner 用来隔离并证明 Evaluator 和 Agent 运行轨迹，不能代表真实 LLM 的泛化质量。

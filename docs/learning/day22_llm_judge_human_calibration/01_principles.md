# Day22：LLM Judge 与人工校准原理

## 1. 今天解决的真实问题

Day21 能精确判断最终状态、工具、参数、步骤、Policy 和错误归因，却很难仅靠枚举规则判断一段解释是否清楚、是否把证据和结论讲明白、是否给出可执行的下一步。LLM Judge 适合补充这些软语义评价，但它本身会波动、有位置偏差，也可能被待评文本中的指令影响，所以不能把一次总分当成真相。

Day22 建立的是“确定性硬门禁 + 经人工校准的语义 Judge”组合体系，而不是用 Judge 取代 Day21。

## 2. 完整操作流程

1. 先运行 Day21 硬门禁，确定最终状态、工具、参数、轨迹和 Policy 是否合格。
2. 只把适合语义判断的解释文本送入 Day22；危险动作不能因为语言表达好而进入放行状态。
3. 使用版本化 Rubric，把解释质量拆成四个有 1–4 分锚点的维度。
4. 构建盲化校准样本：隐藏 Baseline/Candidate、模型名和版本，只保留 Response A/Response B。
5. 两名人工标注者独立给偏好，不查看对方标签；分歧样本再裁决，保留原始分歧而不是只保存最终标签。
6. Judge 通过统一 ModelGateway 做结构化输出，不能返回任意自由文本或额外字段。
7. 每个 Case 判两次：第一次 A/B 原顺序，第二次交换顺序。
8. 在 Judge 外部把 A/B 还原成版本身份，比较两次偏好是否一致，计算顺序敏感率。
9. 将 Judge 的偏好和四维分数与人工裁决比较，计算偏好一致率、平均绝对误差和 ±1 分命中率。
10. 语义门禁只在 Judge 已达到校准阈值时有效；最终发布规则永远是：`确定性硬门禁 AND 经校准的语义门禁`。
11. 报告保留人类分歧、Judge 分歧、维度分、顺序敏感案例和解释边界，不把单一平均分包装成真相。

## 3. Rubric 为什么必须版本化并有分数锚点

如果只问“这个回答好不好，打 1–10 分”，不同标注者和不同模型对“7 分”的理解不一致，分数无法稳定比较。Day22 使用四个具体维度：

### 3.1 Clarity：清晰度

判断客服人员是否能一次看懂结论和原因。它不等于越短越好；短到缺少结论是低分，清楚且无歧义才是高分。

### 3.2 Evidence grounding：证据解释

判断解释是否把已验证事实连接到结论，是否避免编造事实。注意它评价的是“如何解释证据”，不是重新验证 Tool Observation 是否真的存在；证据真实性仍由确定性规则负责。

### 3.3 Reasoning completeness：推理完整性

判断是否覆盖关键冲突、不确定性和处置理由。例如 `timeout` 不等于 `proof_available=false`，解释必须保留这种语义差异。

### 3.4 Actionability：可执行性

判断是否给出明确下一步、执行者和停止/审核条件。它评价表达是否可操作，不判断动作本身是否授权；授权仍归后端 Policy。

每个维度都定义 1、2、3、4 分的含义。Rubric 版本进入 Prompt 版本和 Model Call 记录，Rubric 变化后不能与旧报告直接混算。

## 4. Judge 适合和不适合评什么

### 适合

- 解释是否清楚、简洁且无歧义；
- 是否把给定证据和结论连接起来；
- 是否遗漏关键冲突或不确定性；
- 下一步说明是否具体、可执行；
- 两个合格回答之间的相对语义质量。

### 不适合

- Tool 名称和版本是否存在；
- Tool 参数、订单号和 tenant 是否正确；
- 退款是否获得授权和人工审批；
- Policy、金额、幂等、状态机是否合规；
- 最终状态和错误归因是否客观正确；
- 安全轨迹能否放行。

不适合项都有明确代码、Schema、Policy 或 Trace 可以检查。让 LLM 评价这些确定性事实会更贵、更不稳定，也更难审计。

## 5. 盲化与人工校准的关系

本项目的盲化包含三层：

- Judge 输入只出现 A/B，不出现 Baseline/Candidate、模型名或版本；
- 两名人工标注者只看 A/B，彼此独立，不看对方标签；
- Judge 不接收人工标签，人工裁决也不接收 Judge 结果。

代码可以保证 Judge Payload 盲化和两份独立标注记录；真实人工过程是否严格执行仍需要标注平台权限和流程审计，不能只靠 JSON 声明证明。

人工标签也不是绝对真理。Day22 同时报告人工标注者一致率。本次 8 个合成样本中人工偏好一致率为 87.5%，一个分歧样本经过裁决。保留分歧能提醒我们某些 Rubric 或样本本身存在歧义。

## 6. 为什么要交换 A/B 顺序

如果只判一次，Judge 可能习惯选择第一个或第二个回答。每个 Case 再交换 A/B 判一次，然后把位置偏好还原成版本偏好：

- 原顺序选择 B，交换后选择 A：两次都选择同一版本，顺序一致；
- 原顺序选择 B，交换后仍选择 B：选择跟着位置变化，属于顺序敏感。

本次固定样本检测到 1/8 顺序敏感，即 12.5%。这只能测量顺序敏感，不能代表已经排除长度偏差、措辞偏差、自我偏好、模型家族偏好等所有偏差。

## 7. 结构化输出和后端再校验

Judge 只能返回四维 1–4 分、A/B/tie 偏好、置信度和受控理由码。Pydantic 拒绝额外字段和越界分数；后端还检查偏好与平均分方向一致。例如 B 的平均分更高却声明偏好 A，会被 ModelGateway 记录为 `model_output_invalid` 并拒绝。

结构化输出解决“格式和内部一致性”，不证明 Judge 观点正确；正确性仍要靠人工校准、重复判分和偏差分析。

## 8. 组合质量门禁为什么不能用平均分替代

一个控制 Case 中，Candidate 的语义得分是满分 4.0，但其 Day21 硬安全门禁为失败。组合门禁仍拒绝发布，并记录一次 `judge_override_attempts_blocked`。

最终规则：

`release = hard_gate_passed AND semantic_score >= calibrated_threshold`

Judge 的高分没有权限把 `hard_gate_passed=false` 改成 true。这与 Agent 的模型/后端分工一致：模型处理不确定语义，后端控制确定性安全边界。

## 9. 本次固定校准数据

8 个合成 Case 覆盖 normal、boundary、failure、adversarial：

- 人工标注者偏好一致率：87.5%；
- Judge 与人工裁决偏好一致率：87.5%；
- A/B 交换后的顺序一致率：87.5%；
- 顺序敏感率：12.5%；
- 四维分数平均绝对误差：0.125；
- Judge 分数落在人工裁决 ±1 内的比例：100%；
- Candidate 四维平均分 3.4375，Baseline 为 2.25，合成对照提升 1.1875 分；
- 组合发布决策正确率：100%；
- Judge 高分覆盖硬门禁的尝试被阻止：1 次。

这些数字只验证当前合成校准流程和固定 Judge fixture，不代表生产 Judge 的真实质量。

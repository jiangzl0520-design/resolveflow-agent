## 一、整套知识之间的关系

今天学习的概念不是互相独立的名词，它们共同组成一次 Agent 任务：

```text
用户提出目标
    ↓
History 记录用户原始输入
    ↓
业务层创建结构化 State
    ↓
Context Engine 从规则、State、History、Memory、RAG 中选择本轮信息
    ↓
LLM 根据 Context 决定下一步行动
    ↓
Tool Gateway 校验工具、参数、权限和风险
    ↓
工具执行并产生 Observation
    ↓
Observation 写入 History/运行轨迹，并更新 State
    ↓
Verifier 判断证据是否充分、是否需要继续行动
    ↓
涉及退款等写操作时，依次通过业务规则和人工审批
    ↓
幂等执行写工具并验证真实结果
    ↓
Trace 记录全过程，Eval 判断结果和过程是否都正确
```

Agent 的核心价值出现在这个闭环里：它会根据新的 Observation 改变下一步行动。后端工程的价值则是保证这个闭环不会越权、重复执行或在崩溃后丢失状态。

## 二、普通 RAG 为什么不等于 Agent

普通 RAG 的典型流程是：

```text
用户问题 → 检索文档 → 把文档交给模型 → 生成回答
```

它主要解决“模型缺少外部知识”的问题，路线通常是预先固定的。

Agent 的典型流程是：

```text
明确目标 → 判断缺失信息 → 选择工具 → 观察结果 → 验证 → 修订计划或结束
```

例如处理“未收到包裹并要求退款”：

1. 查询订单。
2. 根据订单状态决定是否查询物流。
3. 如果物流显示已签收但用户否认收货，再查询签收证明。
4. 根据证据决定继续调查、提出退款方案或转人工。

这里第三步是否出现，取决于第二步的结果。系统不是沿固定管道走到底，而是在运行过程中作出受约束的决策，因此属于 Agent。

RAG 可以成为 Agent 的一个工具。Agent 判断什么时候检索、检索什么、证据是否足够以及是否需要继续检索，这就是 Agentic RAG。

## 三、LLM 与后端代码的职责边界

### LLM 负责不确定性的语义判断

- 理解用户目标。
- 从自然语言中提取可能的业务事实。
- 判断当前缺少哪些证据。
- 在多个工具中选择可能适合的下一步。
- 发现自然语言证据之间的矛盾。
- 组织解释和提出处理方案。

### 后端代码负责确定性约束

- 用户、角色和租户权限。
- 退款金额上限。
- 审批记录是否真实存在且仍然有效。
- 审批参数是否与本次执行参数完全一致。
- 幂等、事务、超时、重试和审计。
- 外部系统是否真的完成退款。

判断边界时可以问两个问题：

1. 这个判断是否需要理解模糊语言和开放环境？如果是，LLM 可以参与。
2. 判断错了是否会造成资金、安全、权限或数据一致性问题？如果是，后端必须拥有最终决定权。

LLM 可以提出工具调用，但真正执行前，Tool Gateway 必须重新校验。不能把模型说的“已经审批”当成事实，必须查询审批数据库。

## 四、History、State、Memory、Context 的区别与联系

| 概念 | 解决的问题 | 示例 | 主要特点 |
|---|---|---|---|
| History | 曾经发生过什么 | 用户先说 10086，后来改成 10087 | 原始、按时间追加、不可随意覆盖 |
| State | 当前任务处于什么状态 | `active_order_id=10087`、等待审批 | 结构化、可更新、用于流程控制 |
| Memory | 跨任务以后还值得使用什么 | 用户偏好中文回复 | 长期、经过筛选、需要过期和删除机制 |
| Context | 这一次模型实际看到什么 | 安全规则 + 当前 State + 相关证据 + 工具定义 | 临时组装、受 Token 预算限制 |

它们之间的关系是：

```text
History / State / Memory / RAG / Policy
                  ↓ 选择、排序、压缩、隔离
               Context
                  ↓
                 LLM
```

Context 不是完整聊天历史，也不只是工具结果。第一次调用模型时还没有工具结果，但 Context 仍然可以包含系统规则、用户目标、当前 State 和工具定义。

## 五、用户改口时为什么不能修改 History

用户先说订单号是 10086，后来明确改成 10087，正确处理是：

### History

保留两个事件：

```text
事件 1：用户提供订单号 10086
事件 2：用户纠正，正确订单号是 10087
```

History 保存的是发生过什么。如果直接把 10086 改掉，系统将无法解释之前为什么查询了 10086，也无法完成审计和问题排查。

### State

把当前有效字段更新为：

```text
active_order_id = 10087
```

同时失效所有依赖 10086 得到的派生状态：

- 订单状态；
- 物流状态；
- 签收证明；
- 退款资格判断；
- 退款提案；
- 审批请求。

原因是这些结论都建立在“当前订单是 10086”这个前提上。前提改变以后，结论不能继续使用。

### Context

下一轮 Context 应明确告诉模型：当前有效订单是 10087，用户曾纠正订单号。旧订单结果可以保留在审计轨迹中，但不能作为 10087 的业务证据。

这体现了一个重要的数据原则：

> 原始事件保持不可变，当前视图可以更新；主事实变化时，依赖它的派生数据必须重新计算。

## 六、证据、业务资格、审批、执行是四个不同阶段

正确顺序是：

```text
收集证据
  ↓
判断是否符合业务规则
  ↓
生成具体退款提案
  ↓
人工审批这个具体提案
  ↓
后端再次检查规则和审批
  ↓
幂等执行
  ↓
查询真实状态完成验证
```

### 证据充分不等于已经获得授权

即使证据完全证明用户应该退款，没有人工审批也不能执行高风险退款。

### 人工授权不等于符合业务规则

即使人工批准 150 元，公司规则规定最多只能退款 100 元，后端仍然必须拒绝。

因此至少有两道独立门槛：

```text
business_eligible == true
approval_valid == true
```

只有两者都成立，系统才可以进入实际执行阶段。

## 七、审批为什么必须绑定具体参数

人工批准的不是“以后允许这个 Agent 随意退款”，而是一个具体操作，例如：

```text
工具：refund_order
订单：10086
金额：100 元
原因：未收到货
提案版本：v1
```

模型随后调用 150 元退款时，Tool Gateway 必须发现参数不匹配并拒绝。不能依靠模型主动拒绝，因为模型可能没有注意到变化、误解审批记录或受到 Prompt injection 干扰。

如果确实需要改成 150 元，应创建新提案，重新进行规则检查和人工审批。原来 100 元的审批不能复用。

## 八、Checkpoint、幂等与执行后验证

### Checkpoint 解决“从哪里继续”

每完成一个重要步骤，保存：

- 当前 State；
- 已完成步骤；
- 工具调用及结果；
- 下一步动作；
- 是否等待审批。

进程崩溃后读取 checkpoint，从已确认位置继续，而不是从头猜测。

### 幂等解决“重复请求会不会重复产生副作用”

退款调用必须携带唯一幂等键，例如：

```text
refund:ticket-T001:proposal-v1
```

同一个幂等键重复提交，退款服务只能产生一次有效退款。

### 执行后验证解决“请求返回前崩溃，操作到底成功没有”

如果退款服务已经成功，但 Agent 在保存结果前崩溃，本地状态会显示未知。恢复后必须先根据业务单号或幂等键查询真实退款状态，不能立即再次调用退款。

三者的关系是：

- Checkpoint 保存运行进度。
- 幂等保护重复执行。
- 执行后验证消除外部结果不确定性。

## 九、为什么最终回答正确仍可能评估失败

Agent 评估至少要检查：

- 最终任务是否完成；
- 工具是否选对；
- 参数是否正确；
- 证据是否支持结论；
- 执行轨迹是否合理；
- 是否遵守权限和审批策略；
- 是否出现重复或无用步骤；
- 延迟和 Token 成本是否可接受。

如果 Agent 没有审批就完成了退款，即使最终答案和退款结果都正确，也必须判失败。因为生产级系统要求“结果正确”和“过程安全”同时成立。

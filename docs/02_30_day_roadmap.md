# 30 天路线与每日验收

总投入约 180 小时。每天默认分配：原理与设计 1 小时、结对实现 3 小时、测试/评估 1 小时、总结与面试 1 小时。实际会根据当天难度调整，但不会省略测试、原理整理和面试验收。

## 第一阶段：生产级后端地基（Day 1–5）

### Day 1：需求建模与 HTTP 主链路

- 明确工单、运行、步骤、审批四个核心聚合。
- 建立 FastAPI 工程骨架、配置管理、统一响应和健康检查。
- 实现创建/查询工单的最小 API 和第一组单元测试。
- 验收：能解释一次 HTTP 请求从 ASGI 到数据库返回的完整路径。

### Day 2：PostgreSQL、ORM 与迁移

- Docker Compose 启动 PostgreSQL 和 Redis。
- SQLAlchemy 2、session/transaction、Alembic 迁移。
- 建立 tickets、ticket_events、agent_runs 表。
- 验收：能解释连接池、事务边界、迁移与 `create_all` 的区别。

### Day 3：分层、事件与并发一致性

- Router → Service → Repository 分层。
- 工单状态机、乐观锁、幂等请求键、审计事件。
- 并发更新和重复提交测试。
- 验收：重复请求不能创建两个相同工单，非法状态转移会被拒绝。

### Day 4：认证、RBAC 与多租户边界

- JWT/开发态身份、角色权限、tenant 过滤。
- 资源级鉴权和审计日志。
- 越权访问测试。
- 验收：不是只在前端隐藏按钮，服务端会拒绝跨租户访问。

### Day 5：异步任务、重试、取消与恢复

- API 只负责受理，Worker 处理长任务。
- 指数退避、超时、死信/失败状态、取消令牌。
- API/Worker 传播 request_id 和 trace_id。
- 验收：Worker 中断后任务状态不丢，重试不重复产生副作用。

## 第二阶段：Agent 运行时与人机闭环（Day 6–11）

### Day 6：模型网关与结构化输出

- 统一 LLM Provider 接口、超时、重试、模型配置。
- Pydantic 结构化输出、Prompt 模板与版本号。
- 使用 Fake LLM 做确定性测试。
- 验收：业务层不依赖某一家模型 SDK，非法输出可定位和降级。

### Day 7：工具契约与注册中心

- 实现订单、物流、政策查询三个只读模拟工具。
- JSON Schema、风险等级、权限、超时和标准错误。
- 工具选择与参数校验测试。
- 验收：能区分“模型选错工具、参数错、工具自身失败”。

### Day 8：自己实现最小 Agent Loop

- 实现 observe → decide → act → verify 循环。
- 显式最大步数、时间预算、Token 预算和完成条件。
- 加入循环检测和错误分类。
- 验收：面对不同观察结果会选择不同下一步，而非固定工作流假装 Agent。

### Day 9：LangGraph 状态图与 checkpoint

- 把最小循环映射到状态图节点和条件边。
- 运行状态持久化、暂停、恢复和取消。
- 对比自研循环和框架分别解决了什么。
- 验收：进程重启后可以从 checkpoint 继续，且不会重复已成功步骤。

### Day 10：风险策略与 Human-in-the-loop

- 新增退款提案和写工具。
- 金额、权限、证据充分度的确定性策略。
- 审批、拒绝、修改、超时和人工接管。
- 验收：所有高风险案例都在写操作前暂停，未审批执行数为 0。

### Day 11：MCP 适配与工具服务化

- 把至少一个业务工具作为独立 MCP Server 暴露。
- Agent 侧实现发现/调用适配，保留同一内部 Tool Contract。
- 鉴权、超时、断路和契约测试。
- 验收：能说明 MCP 解决互操作，不替代业务权限和可靠性设计。

## 第三阶段：上下文工程、RAG 与记忆（Day 12–17）

### Day 12：知识入库流水线

- 政策文档解析、按标题语义切块、metadata、版本和有效期。
- 文档去重、增量更新、失败重跑。
- 验收：任何 chunk 可追溯到原文、版本、租户和有效期。

### Day 13：混合检索

- pgvector 语义召回 + PostgreSQL 全文/关键词召回。
- query rewrite、metadata/ACL 过滤、结果融合。
- 构造检索评测集并计算 Recall@k、MRR。
- 验收：能用数据解释向量、关键词和混合检索的差异。

### Day 14：重排、引用与 grounded answer

- rerank、证据去重、冲突检测。
- 最终结论强制携带可验证引用。
- 检索不到或证据冲突时禁止编造。
- 验收：引用精确率可自动检查，过期政策不会被作为有效依据。

### Day 15：Context Builder 与 Token 预算

- 上下文分层、来源标记、优先级、相关性和 Token 预算。
- 工具描述按当前步骤动态选择。
- 记录每个片段进入或被丢弃的原因。
- 验收：长对话下仍保留目标、最新用户修改和关键证据。

### Day 16：短期状态与长期记忆

- 区分原始历史、任务状态、摘要、业务事实和用户偏好。
- 记忆写入门槛、来源、置信度、过期、冲突和删除。
- 验收：长期记忆不是“把所有聊天 embedding 后存向量库”。

### Day 17：上下文安全

- 外部内容标为 data，不允许覆盖 system policy。
- Prompt injection 测试、敏感信息脱敏、知识 ACL。
- 用户改口、陈旧信息和恶意文档测试。
- 验收：恶意知识文档不能诱导工具越权或泄露系统信息。

## 第四阶段：可观测性、评估与数据飞轮（Day 18–23）

### Day 18：全链路 Trace

- OpenTelemetry 串联 API、Worker、Agent、LLM、RAG、Tool、DB。
- Span 记录版本、耗时、Token、重试和状态转移。
- 敏感字段过滤。
- 验收：从一个失败 run 能定位是模型、检索、工具还是业务规则失败。

### Day 19：Metrics、Logs 与 Dashboard

- Prometheus 指标、结构化日志、Grafana 面板。
- 技术指标和业务指标分开呈现。
- 告警规则和 SLO 草案。
- 验收：能回答“今天成功率下降由什么导致”。

### Day 20：Golden Dataset 与 Eval Harness

- 建立正常、边界、失败和对抗四类案例。
- 数据集版本、运行配置、结果持久化。
- 一条命令运行离线评估并输出报告。
- 验收：同一个版本可重复执行，结果可与基线比较。

### Day 21：任务、轨迹和工具评估

- 最终状态、工具选择、参数、步骤效率、策略合规评分。
- 错误归因到 planner/retriever/tool/context/policy/model。
- 验收：最终答案碰巧正确但轨迹危险时仍然判失败。

### Day 22：LLM Judge 与人工校准

- 为解释质量、理由充分性设计 rubric。
- 双盲小样本人工标注，检查 Judge 一致性和偏差。
- 验收：明确 Judge 适合与不适合评什么，不把单一分数当真相。

### Day 23：反馈闭环与版本实验

- 失败轨迹进入待审核池，人工标注后形成新评测案例。
- 对 Prompt/RAG/模型做成对比较。
- 建立发布门禁：安全不退化、核心指标通过。
- 验收：完成一次从失败样本到回归改进的数据闭环。

## 第五阶段：可靠性、性能与交付（Day 24–27）

### Day 24：测试金字塔

- 单元、集成、工具契约、Agent trajectory、API E2E 测试。
- Testcontainers 或独立测试库。
- 验收：核心失败路径都有自动化测试，不只测 happy path。

### Day 25：并发、缓存、成本和延迟

- 并发任务限制、连接池、背压、缓存和请求合并。
- 压测 API 受理链路与 Worker 吞吐。
- 分析 Token 和工具调用成本。
- 验收：提交真实压测环境、脚本、瓶颈和前后对比，不编数字。

### Day 26：故障注入与降级

- 模型超时、MCP 故障、Redis/Postgres 短暂异常、工具部分成功。
- 断路器、降级模型、转人工、恢复和补偿。
- 验收：关键故障都有明确用户体验和数据一致性策略。

### Day 27：CI、容器与发布

- Dockerfile/Compose、lint/type/test/eval CI。
- 配置和密钥管理、启动探针、迁移流程、回滚说明。
- 验收：新环境按 README 可复现启动，合并前自动跑质量门禁。

## 第六阶段：演示、简历与面试答辩（Day 28–30）

### Day 28：人工审批控制台与演示场景

- 轻量页面展示工单、进度、证据、审批和 Trace。
- 准备正常、冲突、注入攻击、工具故障四条演示路径。
- 验收：面试官 5 分钟能看懂业务价值和 Agent 闭环。

### Day 29：项目文档与简历材料

- 架构图、ADR、OpenAPI、数据模型、评估/压测报告。
- 3 分钟和 10 分钟项目讲解稿、STAR 难点故事。
- 简历表述只使用真实测得指标。
- 验收：任何简历数字都能在仓库中找到脚本或报告证据。

### Day 30：最终回归与系统设计答辩

- 从空环境部署、跑全量测试和 Golden Dataset。
- 演练 Agent/RAG/后端/安全/评估系统设计追问。
- 建立后续补强清单：算法岗再补 Transformer/后训练，平台岗再补分布式。
- 验收：能独立解释每个核心设计的原因、替代方案和失败边界。

## 每天的硬性完成定义

一天只有同时满足以下条件才算完成：

1. 当天功能可运行。
2. 正常路径和至少一个失败路径有测试。
3. 原理按实际操作流程整理完成。
4. 关键设计选择记录“为什么”和“没有选什么”。
5. 完成面试问答，错题追问到能独立解释。
